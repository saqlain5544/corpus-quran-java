# Quran Reader App

Read, search, and explore the Quran with full morphology — written in
**Go + vanilla JS/CSS/HTML**, no frontend frameworks, no Node toolchain.

This is a from-scratch rewrite of the previous Next.js implementation
(`quran-reader/`, deleted) using the constraints in `agents.md`:

- Only `quran-uthmani.xml`, `MASAQ.csv`, `hafs.woff2` are trusted for
  primary content. Root meanings are AI-generated (clearly labeled).
- Editorial UI, typography-first, 12-column grid, dark/light themes.
- Keyboard-accessible. `prefers-reduced-motion` respected.
- Memory budget tracked (see `docs/research/integration-report.md`).

## Quick start

```sh
# 1. Pre-process the raw data into gob files (one-time, ~30s).
go run ./pipeline/cmd/build -data ./data -out ./data/processed

# 2. Build and run the server.
go build -o ./bin/quranreader ./backend
./bin/quranreader -addr :8080 -data ./data/processed
# → open http://localhost:8080/
```

## Routes

| Path | What |
|---|---|
| `GET /` | Homepage — list of all 114 surahs. |
| `GET /surah/{id}` | Full surah in paragraph form with hafs.woff2 typography. |
| `GET /surah/{id}/{verse}` | Same, with `#verse-N` anchor auto-scrolled to on load. |
| `GET /search?q=…&type=…` | Search results page (`type` = `english` \| `arabic` \| `root`). |
| `GET /roots` | Paginated root list, sortable by frequency. |
| `GET /root/{root}` | Detail for one root (occurrences + meaning). |
| `GET /about` | Data sources and licence. |
| `GET /api/word?s=…&a=…&w=…` | JSON morphology for a single word. |
| `GET /api/search?q=…&type=…` | JSON search results. |
| `GET /api/roots?page=…&sort=…` | JSON root list. |
| `GET /api/root/{root}/occurrences` | JSON list of all occurrences. |
| `GET /api/health` | Liveness probe. |
| `GET /static/css/{name}.css` | CSS files. |
| `GET /static/js/{name}.js` | JS modules. |
| `GET /fonts/hafs.woff2` | The Uthmani font (WOFF2). |

## Tests

```sh
go test ./...
```

Coverage:
- `loc` — word-location key encoding (round-trip, ordering, bounds).
- `pipeline` — XML/CSV/JSON parsers, build end-to-end round-trip.
- `types` — meta JSON load/save.
- `backend/internal/data` — gob round-trip + sanity lookups.
- `backend/internal/search` — Arabic/English/Root fuzzy match.
- `backend/internal/server` — 28 httptest table-driven cases covering
  every page, every API endpoint, 404s, static assets, and URL
  encoding.

## Memory budget

Detailed measurements are in
[`docs/research/integration-report.md`](docs/research/integration-report.md).
The headline number:

| Phase | RSS | HeapAlloc |
|---|---|---|
| Just-loaded, idle | ~115 MB | ~78 MB |
| Under concurrent load | ~120 MB | ~80 MB |

This is **above** the original 80 MB RSS target set in `agents.md`.
The Go runtime (gob-decoded maps have heavy per-entry overhead) makes
hitting 80 MB impractical without columnar storage or mmap tricks
that are out of scope. HeapAlloc alone is under 80 MB; the rest is
runtime stacks and OS-level bookkeeping.
